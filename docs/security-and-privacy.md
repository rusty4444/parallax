# Security, privacy and preview limitations

Parallax is an independently built Android Matrix client. This is a personal test preview, not a security certification or a claim of Element X parity. Automated transport, storage and widget tests do not establish live end-to-end encryption interoperability.

## Local data

- The Matrix SDK stores session, timeline and encryption state in SQLite inside Android's app sandbox. Device storage encryption and sandbox access controls apply; the database does **not** have an additional SQLCipher layer.
- Message drafts and the durable outbox use OS-backed secure storage, with no plaintext storage fallback. Missing values are distinct from read errors. Automatic Android secure-storage reset on errors is explicitly disabled so a failed read cannot silently erase saved work.
- Appearance preferences are not sensitive message data and use local preferences. Room backgrounds are private app files, not encrypted secure-storage entries.
- Link previews are fetched by your homeserver, not your phone, and are on by default in ordinary rooms (where the server can already read the link). They stay off in encrypted rooms unless you opt in under Settings → Media → Link previews, and rooms whose encryption state is unknown are treated as encrypted. The page titles and image IDs are kept in a per-account file (newest 300) next to the thumbnail cache and deleted on sign-out; only successful previews are saved.
- Thumbnails and avatars are saved in the app's private cache folder (up to 1 GB, oldest removed first): as you see them, and for every chat when you run Settings → Media → Sync thumbnails. Each file holds exactly what the homeserver served for that media ID, so previews from encrypted chats stay encrypted and are decrypted when shown; avatars and media from unencrypted chats are stored as served. File names are hashes, not media IDs. The folder is per session and is deleted on sign-out or when the session ends remotely; Android may also clear it when the phone is low on space. The sync skips invitations, so nothing is fetched from people you haven't accepted.
- Document previews (Word, Excel, PowerPoint, Markdown, CSV and text) are made on the phone. The file is downloaded and decrypted in memory and read on a separate isolate, which is stopped after 20 seconds; it is never written to disk. Parsed previews are kept in memory for the session and dropped on sign-out. The timeline fetches a document for its inline preview only where media previews load automatically (Settings → Media → In chats) and only up to 4 MB; the viewer reads up to 25 MB when you open a file. Parsing is bounded against hostile files: each part of an Office file is inflated up to a fixed limit however large it claims to be, and rows, cells and text are capped. Nothing in a document is run or fetched (no macros, no remote images), and its links go through the same checks as links in messages.
- PDF previews use Android's own PDF renderer, which is a large native library, on files that other people send. It runs in a separate process declared `isolatedProcess`: that process has no permissions, cannot open the app's files or keys and has no network access. The app hands it the decrypted file as a file descriptor and gets pictures of the pages back. On Android 11 and later the file is held in memory only; on Android 7 to 10 it is a private temporary file that is deleted before the renderer reads it, so no path leads to it and it is gone when the preview closes or the app stops. A PDF that crashes the renderer takes down only that process, and one that hangs it is abandoned after 30 seconds (20 for a page). Page sizes and pixel counts are limited on both sides. The same limits apply as for other documents: up to 4 MB for the thumbnail in the timeline, and only where media previews load automatically; up to 25 MB when you open the file. Thumbnails are kept in memory for the session (24 at most) and dropped on sign-out. Scripts, forms and links in a PDF do nothing, and a password-protected PDF is not opened.
- Your most recent chats (up to eight) are given to Android as sharing shortcuts, so the share menu and the launcher can suggest them. Each one is the chat's name, its room ID and a small picture (the avatar thumbnail, or an initial). Android stores them itself, outside the app's storage and screen lock, and shows them to whoever is using the unlocked phone. Nothing is published while a screen lock PIN is set. The shortcuts are removed when a PIN is set, when you sign out and when the account changes. An app cannot remove a shortcut you pinned to the home screen; Parallax disables it instead. Tapping a suggestion never sends by itself: Parallax shows what is being shared and waits for Send.
- Android application backup and device-transfer backup are disabled. This does not protect a compromised/rooted device or a running, unlocked app.
- A native media player needs a decrypted temporary file for audio/video playback. Cleanup joins the work and disposes the player before removing its source. A native operation that never finishes, failed player disposal or process death can prevent cleanup; temporary files are not an encrypted media vault. Explicitly saved attachments belong to the destination the user chooses and are outside this cleanup policy.
- Voice recording requests microphone permission only for a user-initiated recording. Recording and preview are local operations; sending is a separate action. Do not record sensitive material on an untrusted device.
- Signing certificates must match to update an existing preview. Uninstalling to bypass an update error removes the Matrix session and local encryption keys. Keep a verified recovery credential before changing installations.

## Network and encrypted sends

- Entered, discovered and restored Matrix homeserver URLs must use HTTPS without embedded credentials. Passwords and bearer tokens must not be sent to an insecure discovered URL.
- Encrypted-room text, thread replies, media and retries retain the app's recipient-trust checks and final HTTP send guard. Losing encryption or session ownership is an error, not permission to fall back to plaintext.
- Encrypted attachments are encrypted before upload. The queued upload route sends to the configured HTTPS homeserver without automatic redirects, bounds the response, and has an aborting overall deadline. A progress indicator measures bytes handed to the transport, not server acknowledgement.
- A durable outbox entry is saved before transmission. Queued acceptance is not delivery: sending/failed state and explicit retry/discard remain visible. Interrupted entries are not automatically replayed after restart. A cancelled or timed-out request may already have reached the server; cancellation cannot retract a delivered event. Stable transaction IDs reduce duplicate event delivery when retrying within the same Matrix transaction scope.
- The legacy multi-photo batch remains sequential and non-atomic. Some photos can be delivered before a later photo fails. It is not a single transactional message.
- Typing notifications and relation-only reactions remain disabled in encrypted rooms because the resolved SDK can expose relation metadata or prepare key sharing before recipient approval.
- Read-receipt preferences control automatic room-open receipts. A Matrix homeserver can still observe connections, memberships, encrypted traffic, event sizes and timing. Encryption does not conceal all metadata.

## Authentication and recovery

Browser sign-in uses the configured homeserver/identity provider and the app's dedicated callback. The callback, state/nonce and account ownership are validated before accepting authentication results. OIDC compatibility depends on the provider's supported registration and authorisation flow; an automated callback test is not a real-provider acceptance test.

Transient refresh/network failures must not erase the existing device or encryption identity. Soft-logout re-authentication is distinct from replacing an account. New-account setup and partial repair retain the existing conservative checks: no automatic destructive reset or recovery-key rotation, no inferred absence of keys after an incomplete server response, and no account replacement during an in-flight crypto setup. Save the displayed recovery credential before server writes. Do not run setup for the same account simultaneously on another client.

Android blocks screenshots and recent-app previews while recovery credentials are displayed. Other message and media screens are not represented as screenshot-proof.

## Optional push service

Push is disabled by default and requires the user's own Firebase project and Matrix-compatible HTTPS push gateway. No borrowed gateway, service account or Firebase project credentials are bundled. Configuration alone does not demonstrate live delivery. Notification permission, token creation and pusher registration require complete configuration and explicit opt-in; disabling push or signing out must retire that account's registration.

Enabling push introduces Google Firebase Cloud Messaging (or your UnifiedPush distributor) and the configured gateway as external services. They can receive device registration and routing metadata — room and event IDs, counts and timing — but never message content: pushers use `event_id_only`, and the gateway must not add content.

Notifications show the sender, message text and media previews, like Element X. That content is fetched from your homeserver and decrypted **on this device** after a push arrives: by the running app's Matrix client, or, when Parallax is not running, by a short-lived read-only client that opens the local database without syncing, uploading keys or writing. If fetching or decrypting fails or takes too long, the generic “New message” alert is shown instead. Settings → Notifications turns message content (and separately media previews) off; with content off the generic alert is used and nothing is fetched. Notifications use Android's *private* lock-screen visibility, so a secure lock screen hides their content when you choose to hide sensitive notifications in system settings; on an unlocked or insecure screen, other people can read notification content.

Decrypted previews are bounded downloads, re-encoded and written to `cache/notification_media/` in the app sandbox; Android's system UI reads only the image attached to a posted notification through a non-exported FileProvider. Recent notification lines, the notification settings and quick replies waiting to be sent are stored in the private app support directory (excluded from backup). They are scoped to one account and device and deleted on sign-out. Quick replies are only sent by the running app through the normal recipient-trust and encryption guards, never from a background isolate.

Notification navigation and actions must be bound to the active account/device, not merely a room ID from an old payload. See [push setup](push-notifications.md) for the actual configuration contract and limitations.

## Required live acceptance checks

Use disposable accounts before trusting this preview with important messages:

- Two-client text/media/thread encryption, first-use trust, identity changes and rejected trust.
- Verification in both directions, mismatch/cancel, recovery and guarded partial repair.
- Password, SSO and OIDC sign-in against the actual provider; expired-token refresh and soft logout without changing device identity.
- Gallery/document/keyboard media, voice recording, audio/video playback and lifecycle interruption on a physical Android device.
- Directory, thread pagination, Spaces hierarchy/join, favourites and receipts against the actual homeserver.
- Opted-in push delivery, token rotation, disable/logout and stale-notification rejection using the user's own infrastructure.
- Rich notifications with the app open, in the background and closed: decrypted text, image previews, mentions, invites, ringing calls, quick reply (including while closed) and the generic fallback when keys are missing.

Calls/Element Call interoperability, production signing and a complete independent security audit are outside this preview. Consult release notes for the exact automated checks and device smoke tests actually executed; an unchecked live test must not be treated as passed.
